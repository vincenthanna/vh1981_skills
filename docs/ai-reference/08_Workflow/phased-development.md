# phased-development

대규모 코드 변경을 단계별로 설계/구현/검증하는 프로세스 템플릿.
각 단계에서 빌드+테스트를 통과해야 다음 단계로 전진한다.

## 개요

복잡한 코드 변경을 안전하게 수행하기 위한 구조화된 프로세스.
Phase 0(분석)에서 요청을 명확화하고 작업을 분해한 뒤,
Phase 1~N(검증 루프)에서 안전도 높은 것부터 순서대로 구현하며 매 단계 검증한다.

## 트리거

대규모 리팩토링, 프레임워크 전환, 멀티 파일 변경, API 교체 등
단일 커밋으로 처리하기 어려운 복잡한 코드 변경 작업 시 사용.

---

## Phase 0: 분석 및 Phase 분류

### 0-1. 요청 파악 및 명확화

요청의 의도, 범위, 제약 조건을 정확히 이해한다. 모호한 부분은 구현 전에 해소한다.

```
{USER_REQUEST}

위 요청을 분석하라.
- 관련 코드를 모두 읽고 현황을 파악하라.
- 요청의 목표가 무엇인지 한 문장으로 정리하라.
- 다음 항목에서 모호하거나 불명확한 부분을 식별하라:
  - 범위: 어디까지 바꾸는 것인지 (이 파일만? 연관 파일도?)
  - 방식: 여러 접근법이 가능할 때 어떤 것을 선택하는지
  - 제약: 유지해야 할 기존 동작, 호환성, 성능 요건
  - 기준: 완료를 어떻게 판단하는지 (테스트, 산출물, 성능 수치)
- 모호한 항목이 있으면 사용자에게 질문하라. 추측하지 마라.
```

**사용자 확인을 받은 후** 다음 단계로 진행한다.

### 0-2. 접근 방식 결정

목표를 달성할 수 있는 접근법을 도출하고, 하나를 선택한다.

```
목표 달성을 위한 접근 방식을 검토하라.
- 가능한 접근법을 나열하라.
- 각 접근법에 대해 평가하라:
  - 변경 범위 (수정 파일 수, 영향받는 컴포넌트)
  - 장점 / 단점
  - 리스크 (호환성, 되돌리기 난이도, 디버깅 어려움)
- 추천 접근법과 그 근거를 제시하라.
```

**사용자 확인을 받은 후** 다음 단계로 진행한다.

### 0-3. 작업 분해

확정된 접근 방식을 개별 작업 단위로 분해한다.

```
- 선택한 접근법을 구현하기 위한 변경 사항을 개별 작업 단위로 분해하라.
- 각 작업의 안전도(영향 범위, 되돌리기 난이도, 의존성)를 평가하라.
```

### 0-4. Phase 분류 및 순서 결정

분해한 작업을 **안전도** 기준으로 phase에 배치한다.
순서는 반드시 **쉽고 안전한 것 → 어렵고 복잡한 것**.

```
분해한 작업들을 phase로 분류해라. 다음 기준으로 정렬:

안전도 높음 (먼저 실행):
  - 동작 변경 없음 (include 추가, 타입 선언, 빌드 설정)
  - 단일 파일 수정
  - 독립적 (다른 변경에 의존하지 않음)
  - 실패 시 되돌리기 쉬움

안전도 낮음 (나중에 실행):
  - 여러 파일 동시 수정 필요 (부분 전환 불가)
  - 기존 API/인터페이스 제거
  - 런타임 동작 변경
  - 실패 시 디버깅 어려움

각 phase에 대해:
  - 무엇을 변경하는지
  - 왜 이 순서인지 (의존성, 안전도)
  - 예상 리스크
를 명시하라.
```

### 0-5. 리스크 평가 (대규모 변경 포함 시)

복잡한 phase가 있으면 구현 전에 상세 평가를 수행한다.

```
Phase {N}에 대해 상세하게 평가해보자.
 - 변환시 발생할 수 있는 문제점 검토
 - 기존 기능 중에 영향받는 부분이 있는지 보자.
 - 로직의 복잡성을 늘리는 등의 문제점이 있는지도 검토하자.
 - 그 외 네가 생각하는 판단 기준점들을 많이 넣어라.
```

---

## Phase 1~N: 검증 루프

### 작업 방법 지시 (첫 phase 시작 전 1회)

```
아래와 같이 일해라.

# 작업 방법

각각의 phase 마다 수정을 한 후에 다음 작업을 통해 제대로 동작하는지 검증한다.

1. 수정 적용
2. {BUILD_DIR} 에서 빌드하고 설치
    - {BUILD_COMMAND}
3. {TEST_DIR} 으로 가서
    - {TEST_COMMAND}
4. {SUCCESS_CRITERIA} 이면 일단 문제 없는것이다.
5. 하지만 {LIMITATION} 이므로, 네 수정 내용에 대해 네가 최대한 정적으로
   잘 분석하고 평가해서 문제일 수 있는 부분들을 수정해야 한다.
6. 다 되면 다음 phase로 전진.
```

### 구현 지시 (phase별)

```
Implement the following plan:

# Phase N: {PHASE_TITLE}

## Context
{왜 이 변경이 필요한지. 이전 phase에서 완료한 것. 이 phase의 목표.}

## 수정 대상 파일
| 파일 | 역할 |
|------|------|
| `{path/to/file}` | {이 파일에서 할 일 요약} |

## 참조 파일 (읽기 전용)
| 파일 | 참조 내용 |
|------|-----------|
| `{path/to/reference}` | {무엇을 참고하는지} |
```

### Sub-Phase 분할 원칙

| 분할 기준 | 설명 |
|-----------|------|
| **a: 빌드 준비** | include/타입 추가만. 동작 변경 없음. 컴파일 통과가 목표. |
| **b: 핵심 전환** | 실제 로직 교체. 부분 전환 가능 여부에 따라 하나 또는 여러 sub-phase. |
| **c: 정리** | warning 제거, dead code 삭제, 기본값 조정. |

### Phase 평가 (phase 완료 후)

```
phase {N} 적용 관련 평가해라.
```

## 완료 보고

모든 phase가 완료되면 전체 작업을 정리한 보고 문서를 작성한다.

### 보고서 구조

```markdown
# {작업 제목} 완료 보고

## 개요
- **목표**: {Phase 0에서 명확화한 요청 목표 한 문장}
- **기간**: {시작일} ~ {완료일}
- **Phase 수**: {N}개

## 변경 요약
| Phase | 제목 | 변경 파일 수 | 핵심 내용 |
|-------|------|-------------|----------|
| 1 | {제목} | {N} | {한 줄 요약} |

## 수정된 파일 목록
| 파일 | 변경 유형 | 설명 |
|------|----------|------|
| `{path}` | 수정/생성/삭제 | {무엇이 바뀌었는지} |

## Phase별 상세
### Phase 1: {제목}
- **변경 내용**: {무엇을 했는지}
- **검증 결과**: {빌드/테스트 통과 여부, 산출물}
- **발견 사항**: {예상 못한 문제, 해결 방법}

## 검증 결과
- 빌드: {성공/실패}
- 테스트: {결과 요약}
- 정적 분석: {잔존 참조 없음 확인 등}

## 주의사항 (구현 중 발견)
- {향후 같은 패턴 작업 시 알아야 할 것들}

## Before / After
| 항목 | Before | After |
|------|--------|-------|
| {비교 항목} | {이전} | {이후} |
```

### 보고서 저장 위치

`docs/projects/{project-name}/report-{YYYY-MM-DD}.md`

## 검증 절차 체크리스트

```
[ ] 빌드 성공 (error 0, 신규 warning 없음)
[ ] 설치 완료
[ ] 테스트 실행 — 크래시 없음
[ ] 테스트 산출물 생성 확인
[ ] 정적 분석 — 제거한 심볼의 잔존 참조 없음
[ ] 정적 분석 — 새로 추가한 include의 전이 의존성 확인
```

## 변수 치환 참조

| 변수 | 설명 | 예시 |
|------|------|------|
| `{USER_REQUEST}` | 사용자의 원본 요청 | `cuOSD로 전면 전환해라` |
| `{BUILD_DIR}` | 빌드 디렉토리 | `d-platform/cpp/gst-nvdsosd-custom` |
| `{BUILD_COMMAND}` | 빌드+설치 명령 | `make clean && make -j32 && make install` |
| `{TEST_DIR}` | 테스트 실행 디렉토리 | `d-platform` |
| `{TEST_COMMAND}` | 테스트 실행 명령 | `export DB_URL="" && python3 app.py` |
| `{SUCCESS_CRITERIA}` | 성공 판단 기준 | `SIGSEGV 없이 종료 + 출력 파일 생성` |
| `{LIMITATION}` | 자동 검증의 한계 | `실제 영상을 보고 잘 그려졌는지 확인은 못함` |
