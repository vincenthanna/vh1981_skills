## PTS 보정 알고리즘 v2 개발 과정에서 사용한 핵심 프롬프트들

### 1. 데이터 검증
vision_data_xxx_fixed.csv 파일들을 모두 검증해라. (총 60개) frame_id가 모두 1씩 증가하고 시간이 뒤집어지지 않았는지.

### 2. Burst 패턴 분석
burst 가 연속으로 시간이 1씩만 증가하거나 시간이 동일하거나 해도 해결이 될까?

### 3. Lock-in 원인 분석
lock-in 발생 시의 timestamp 들을 좀 출력해 봐라. (real ts, output ts)

### 4. 설계 의도 확인 + 구현 검증
아까 말했던 다음 내용이 pts-correction-algorithm-v2.md 와 시뮬레이터 코드에 모두 적용 되었어? : 보정이 크게 정확해야 할 필요는 없고, 기대값과 실제값이 fps 로 구한 diff의 30% 이내로 들어오면 그냥 실제값을 사용하고 보정기능을 초기화해도 될 것 같다. 적당하게 보정하고 어느정도 돌아왔다 싶으면 그만두고 하는 식으로 하고 싶은것이다.

### 5. 문서 + 코드 동시 수정 + 전체 재검증
그러면 문서 + 시뮬레이터 코드 둘 다 수정해라. 그리고 *_diff.csv 파일 모두 지우고 모든 vision_data_xxx_fixed.csv 파일에 대해 다시 시뮬레이터 돌리고 결과 분석 하자.

### 6. 이상값 원인 추적
max|diff| 가 800ms 인 이유를 lock-in 때처럼 timestamp 출력해서 보여줘라

### 7. 평가 기준 반복 조정
- max|diff|는 평가 기준에서 빼고 수정률이랑 연속 수정 기준으로만 다시 종합 평가해라. diff의 경향성도 판단하라.
- burst 프레임 수를 세서 burst프레임수/전체 프레임 수 퍼센티지 + 20% 보다 작으면 문제없음으로 판정하자.
- 연속 수정 실패 갯수는 10초 기준으로 하자.(5fps * 10 = 50)
- 수정률 기준은 평가에서 제외하자.

### 8. 최종 문서화
지금까지 내용 정리해서 문서 업데이트해라.

## 핵심 패턴
- 설계 철학을 먼저 명확히 전달 (적당하게 보정하고, 돌아왔다 싶으면 그만두고)
- 시뮬레이터로 전체 데이터 검증 → 문제 발견 → 원인 분석 → 수정 → 재검증 반복
- 평가 기준을 데이터 특성에 맞게 반복 조정
- 문서와 코드를 항상 동시에 수정하여 일관성 유지
