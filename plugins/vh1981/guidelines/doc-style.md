# 문서 스타일 가이드

사람이 읽는 markdown 문서에 적용한다 (예: 작업 정리, 구현계획, handoff, 설계 문서, README).
코드, 커밋 메시지, CLAUDE.md 자체에는 적용하지 않는다.
한 화면 이내의 짧은 메모에는 "구조" 절의 요약 규칙을 생략해도 된다.

## 원칙

문서의 실행 가능성은 정밀 데이터(경로, file:line, 커맨드, 파라미터, ID)에서 나온다.
이것들은 절대 생략하지 말고 코드블록, 표, 별도 줄에 격리한다.
설명은 완전한 문장으로 쓰되 간결하게 쓴다. 목표는 장황함이 아니라,
생략 때문에 의미가 두 갈래로 읽히는 일을 없애는 것이다.

## 구조

- 문서 상단에 3~5문장 prose 요약을 둔다. 무엇인지, 결론이 무엇인지, 현재 상태와 다음 할 일,
  대기 중인 결정이 무엇인지를 문장으로 쓴다.
  요약 표를 곁들여도 되지만 문장 요약을 표로 대체하지 않는다.
- 역피라미드로 쓴다. 결정과 결론과 현재 상태를 먼저, 근거와 세부는 뒤에.
- 섹션을 문장으로 시작할 때 그 첫 문장은 섹션의 결론이어야 한다.
  섹션 내용의 예고("이 섹션에서는 ~를 설명한다")는 쓰지 않는다.
- 문서 1개 = 목적 1개. spec, 구현 계획, 결정 기록, 시행착오 로그를 한 문서에 몰아넣지 않는다.
  시도했다 버린 방법은 별도 부록으로 빼거나 삭제한다.
- 동일 정보는 문서에 1회만 쓴다 (상단 요약은 예외). 상단 요약이 있으므로
  마무리 요약 섹션은 만들지 않는다.
- 문단은 7행, 목록은 7항목을 넘기지 않는다. 넘치면 문체를 압축하지 말고 내용을 나누거나 줄인다.

## 문장

- 완전한 문장으로 쓴다. 조사와 서술어를 생략하지 않는다.
  - BAD: `본 문서 = A + B 통합`
  - GOOD: `이 문서는 A와 B를 하나로 합친 것이다.`
- 본문 문장 안에서 기호로 서술을 대체하지 않는다. 기호는 관계(원인인지, 순서인지, 동치인지)를
  모호하게 만든다. 관계는 동사로 쓴다: `A → B` 대신 "A가 B를 호출한다".
  기호는 코드블록과 다이어그램 안에서만 쓴다. em dash(—)로 두 절을 잇는 것도 같은 기호 서술이다. 마침표로 나누거나 동사로 잇는다.
- 헤딩, bullet, 문단 첫머리에 핵심 명사(파일명, 기능명)를 앞세운다.
  "또한", "참고로", "이 섹션에서는" 같은 서두 채움말을 쓰지 않는다.
- 출처, 예외, 조건을 괄호로 겹쳐 우겨넣지 않는다. 다음 문장으로 뺀다.
- 식별자와 파일명은 영어 그대로, 설명은 한국어 문장으로 쓴다.

## 표

- 표는 자유롭게 쓴다. 특히 비교(옵션 A vs B, before/after, 측정값 대조)에는 표가 문장보다 낫다.
- 표에서 내릴 결론이 있으면 표 앞이나 뒤에 1문장으로 쓴다. 표의 존재를 알리는 문장은 쓰지 않는다.
  - BAD: `아래 표는 두 방식을 비교한 것이다.`
  - GOOD: `지연시간이 중요하면 A, 메모리가 부족하면 B를 쓴다.`
- 셀 하나에는 값 하나만 넣는다. 예외와 출처는 표 아래 문장이나 각주로 뺀다.

## 강조, 상태, 참조

- 볼드는 아껴 쓴다. 전부 강조하면 아무것도 강조되지 않는다.
- 인라인 코드(백틱)는 실제 식별자, 경로, 커맨드에만 쓴다. "백틱 안은 리터럴"이라는 신호를 지킨다.
- 상태는 단어로 쓴다(완료, 진행중, 미착수, 미검증). 상태 표시와 GOOD/BAD 예시 마커 외의
  장식 이모지는 쓰지 않는다.
- 교차참조는 좌표만 던지지 않는다. 무엇이 있는지 한 문장으로 설명하고 위치를 붙인다.
  - BAD: `상세는 §3 참고`
  - GOOD: `데이터 회수 절차는 §3 에 있다.`
- 테스트나 실행으로 확인하지 않은 항목은 "미검증"으로 표시한다.
  "성공적으로", "견고한" 같은 자기평가 형용사를 쓰지 않는다.

## 구현계획(plan) 문서 전용

Phase마다 아래 골격을 그대로 사용한다:

```
### Phase N — <이름>
목표: <한 문장>
변경 파일: <경로 목록, 코드블록>
작업 내용: <완전한 문장의 bullet, 항목당 1~3문장>
완료 기준: <검증 가능한 조건 한 줄>
```

- 결정 사항은 항목마다 "결정됨 + 근거" 또는 "미결 + 제안 기본값"을 명시한다.
- 상단 요약에 30초 안에 파악해야 할 것을 반드시 포함한다.
  현재 상태, 다음 할 일, 대기 중인 결정이 그것이다.

## 시각 자료

흐름, 구조, 비교, 수치가 있는 문서에는 도식이나 표를 넣는다. markdown에서는 mermaid 도식과 표를 쓰고, 그래프와 애니메이션이 필요하면 HTML 보고서로 만든다.
무엇을 언제 어떤 형태로 그릴지는 `output-principles.md` 의 "시각 자료를 기본으로" 절이 정본이다. 문장 문체의 원칙(쉬운 기술 문체)도 같은 문서에 있다.
이 문서는 문서의 구조와 문장 규칙의 정본이고, `output-principles.md` 는 그 위에 문체와 시각 자료를 얹는다. 두 문서가 다르게 읽히면 구조와 문장 형식은 이 문서를, 문체와 시각 자료는 `output-principles.md` 를 따른다.

## 하지 말 것

- 삭제해도 의미가 변하지 않는 문장: "이 섹션에서는 ~를 설명한다", "아래 표는 ~를 보여준다"
- 한 줄에 참조 여러 개를 가운뎃점으로 이어붙이기
- 문서 전체를 bullet만으로 채우기. 체크리스트와 인벤토리 문서는 예외.
- ASCII 다이어그램으로 본문 설명을 대체하기. 다이어그램은 보조이며 해설 문장을 병행한다.
  코드블록 안의 디렉터리 트리는 예외로 허용.
- 문서 갱신 시 추가만 하고 무효화된 내용을 남겨두기. 이력은 git이 담당한다.
