# 보고서·문서·설명 작성의 기본 원칙

이 문서는 Claude가 보고서, 조사 문서, devlog, 설명을 만들 때 따르는 기본 원칙이다. 출발점은 Karpathy의 글과 그에 이어진 실험이다(`references/karpathy-understanding-llm-outputs.md`).
핵심은 두 가지다. 글은 "쉬운 기술 문체"로 쓰되 사실과 도메인 용어를 잃지 않고, 이해를 돕는 그림, 그래프, 차트, 애니메이션을 기본으로 넣는다.
사용자가 "이해하기 쉽도록 이미지/그래프/차트/애니메이션을 적극 사용"이라고 매번 붙이던 요구가 이제 기본값이다. 붙이지 않아도 이 원칙을 따른다.
문서의 구조와 문장 규칙은 `doc-style.md`, 바깥으로 보낼 짧은 글은 humanizer 스킬이 맡는다. 이 문서는 그 둘 위에 얹는 원칙이다.

## 1. 사람의 일은 이해와 감독이다

LLM이 일을 더 많이 대신할수록, 사람은 결과를 읽고 판단하는 데 시간을 쓴다. 그래서 산출물의 목적은 "다 적었다"가 아니라 "읽는 사람이 빨리, 바르게 이해했다"이다.
결과를 내기 전에 이렇게 묻는다. 읽는 사람이 이것만 보고 무엇이 일어났는지, 무엇이 결정됐는지, 무엇을 해야 하는지 알 수 있는가.

## 2. 형식의 사다리

이해를 돕는 힘은 아래로 갈수록 크다. 내용이 허락하는 한 한 단계 더 아래의 형식을 고른다.

| 단계 | 형식 | 이 저장소에서 쓰는 수단 | 고르는 때 |
|---|---|---|---|
| 1 | 쉬운 문체의 글 | markdown, 채팅 답 | 모든 산출물의 바탕 |
| 2 | 도식, 표, 그래프 | markdown 안의 mermaid, 표 | 흐름, 구조, 비교, 수치가 하나라도 있으면 |
| 3 | 상호작용하는 HTML | `vh1981:techreport`, `vh1981:md-to-html`, kb daily/weekly log | 읽는 사람이 따로 있는 보고서, 단계로 보여 줘야 이해되는 기전, 많은 수치 |
| 4 | 설명 영상 | 요청할 때만 | 사용자가 영상이나 애니메이션 설명을 원할 때. 음성 API 키나 로컬 도구가 필요하므로 기본값이 아니다 |

같은 내용을 글로 두 문단 쓸 것이 도식 하나로 끝나면 도식을 그린다. 쓰고 버려도 되는 HTML이나 작은 도구를 만드는 것을 주저하지 않는다. 한 번 이해하는 데 쓰고 유지보수하지 않아도 된다.

## 3. 쉬운 기술 문체

ASD-STE100은 항공기 정비 문서를 위한 통제 영어다. 엄격하게 적용하면 실험에서 사실의 47%가 사라졌고, 느슨하게 적용하면 8.5%만 사라졌다. 그래서 규격을 그대로 쓰지 않고, 그 정신을 한국어에 맞춰 약 80%만 가져온다.

지키는 것:

- **한 문장에 생각 하나.** 절차 문장에는 지시를 하나만 둔다. 설명 문장이 두 줄을 넘기면 나눈다.
- **같은 대상에는 항상 같은 말.** 동의어를 돌려 쓰지 않는다. 프로젝트 전용 조어나 은유를 새로 만들지 않는다. 이미 있는 이름(파일, 함수, 지표, 티켓)을 그대로 쓴다.
- **도메인 용어와 식별자는 그대로.** 쉬운 말로 풀어 쓰다가 용어를 바꾸면 사실이 사라진다. 처음 나올 때 한 줄로 설명하고, 그 뒤로는 같은 용어를 쓴다.
- **빠뜨리지 않는다.** 주어, 조사, 서술어를 줄여 전보체로 쓰지 않는다(`doc-style.md`).
- **능동형과 명령형.** 할 일은 "X를 한다"로, 위험은 "무엇을 하지 않는다"를 먼저 쓰고 그 이유를 뒤에 쓴다.
- **문단 하나에 주제 하나.** 문단은 6문장 안팎에서 끊는다. 복잡한 조건이나 단계는 세로 목록으로 쓴다.
- **흐릿한 말 대신 셀 수 있는 말.** "명확하게", "효율적으로", "견고하게" 대신 숫자, 조건, 관측값을 쓴다.

지키지 않는 것:

- 영어 단어 수 제한(20, 25단어)과 승인 단어 사전은 한국어 문서에 적용하지 않는다.
- 쉬운 문장을 위해 사실, 수치, 단서, 경로를 빼지 않는다. 쉬워졌지만 사실을 잃었다면 실패다.

## 4. 시각 자료를 기본으로

시각 자료는 장식이 아니라 설명의 본체다. 넣을지 말지는 이 질문으로 정한다: **이 그림이 없으면 읽는 사람이 무엇을 놓치는가?** 답이 있으면 넣고, 없으면 넣지 않는다.

| 전달할 것 | 형태 |
|---|---|
| 처리 흐름, 구조, 의존 관계 | 도식(mermaid flowchart, 상자와 화살표). 문제 지점만 강조색 |
| 두 조건, 여러 후보의 차이 | 표, 막대 그래프. 차이 자체가 메시지면 그 간격에 이름을 붙인다 |
| 시간에 따른 변화, 누적 | 꺾은선. 기준선을 함께 그린다 |
| 분포 | 히스토그램이나 상자 그림. 평균 하나로 끝내지 않는다 |
| 기전, 원리, 단계 | 단계 도식. HTML이면 단계별 애니메이션 |
| 전후 비교 | 나란히 놓은 표나 그림. HTML이면 같은 자리에서 바뀌는 토글 |
| 비율 | 표. 원형 차트는 쓰지 않는다 |

형식별로 쓰는 법이 다르다.

- **markdown 문서(devlog, 계획, handoff):** mermaid 도식과 표를 쓴다. 수치 그래프가 꼭 필요하면 데이터 표를 먼저 두고, 그래프는 techreport나 md-to-html로 만든 HTML에 둔다. ASCII 그림으로 도식을 대신하지 않는다.
- **HTML 보고서:** 인라인 SVG만 쓴다. 외부 이미지, CDN, 폰트를 쓰지 않는다. 숫자는 그림 안에 직접 적고, 색만으로 구분하지 않으며, 다크 모드를 지원한다.
- **애니메이션:** 설명할 때만 쓴다(단계 보여 주기, 등장 순서, 전후 비교). 자동 반복은 하지 않고, 0.4초 안에 끝내며, 멈춘 상태가 최종 상태여야 한다. `prefers-reduced-motion` 을 처리한다. 세부 규칙과 부품은 `vh1981:techreport` 에 있다.
- **채팅 답:** 비교는 표로, 흐름은 짧은 목록이나 작은 도식으로 쓴다. 길어지면 HTML 보고서를 제안한다.
- **개인정보:** 얼굴, CCTV 크롭, 내부 화면 캡처 같은 이미지는 넣지 않는다. 수치, 표, 도식으로 대신한다.

## 5. 도식과 그림도 사실 확인 대상이다

Karpathy 글에 붙은 정리표조차 사전 항목 세 줄이 틀렸다. LLM이 만든 도식, 표, 그래프는 글과 똑같이 근거를 확인한다.
그래프의 숫자는 데이터에서 직접 가져오고, 데이터 출처(파일, 명령, 측정)를 그림 아래나 본문에 적는다. 확인하지 못한 수치는 "미검증"으로 표시한다.

## 6. 적용 범위

| 산출물 | 적용 |
|---|---|
| devlog 조사 문서, history, README | 2~5절 전부. 시각 자료는 mermaid와 표 |
| techreport, kb daily/weekly log, md-to-html | 2~5절 전부. 시각 자료는 인라인 SVG와 애니메이션 |
| 계획, 설계, handoff 문서 | 2~5절. 구조는 `doc-style.md` 가 우선 |
| Slack, PR, 메일 초안 | 3절과 humanizer. 시각 자료는 필요할 때 링크로 |
| 코드, 커밋 메시지, 코드 주석 | 적용하지 않는다 |
