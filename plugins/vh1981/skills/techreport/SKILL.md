# 기술 보고서 생성

조사나 측정을 끝낸 뒤, 그 내용을 **읽는 사람이 혼자 이해할 수 있는 단일 HTML 문서**로 만들고
상시 웹서버에 올린다. devlog 가 *기록*이라면 이 스킬은 *전달*이다.

기본 원칙은 `${CLAUDE_PLUGIN_ROOT}/guidelines/output-principles.md` 다. 쉬운 기술 문체와 시각 자료 우선이 이 스킬 전체에 적용되고, 아래 절들은 그 원칙을 HTML 보고서에서 구현하는 방법이다.

## 0. 먼저 확인할 것

보고서를 쓰기 전에 두 가지를 정한다. 묻지 말고 판단하되, 답이 갈리면 한 번만 확인한다.

| 질문 | 기본값 |
|---|---|
| 읽는 사람이 이 분야를 아는가 | **모른다고 가정한다.** 0장(아주 쉬운 설명)과 용어집이 기본 포함 |
| 개인정보·민감 이미지가 들어가는가 | **넣지 않는다.** 수치·표·도식으로 대체 (§4) |

### 저장 위치

보고서는 활성 devlog 프로젝트 안에 둔다. 서버가 이 트리를 주제별로 묶어 보여주기 때문이다.
활성 프로젝트는 `vh1981:devlog` 의 "Resolving the active project" 규칙으로 정한다. 활성 프로젝트가 없으면 어느 프로젝트에 둘지 한 번 묻는다.

```
docs/devlog/<project>/NN_<slug>.html     # 새 보고서: 프로젝트의 다음 빈 NN 번호
docs/devlog/<project>/NN_<topic>.html    # 기존 조사 문서 NN_<topic>.md 하나를 보고서로 만든 경우: 같은 stem
```

보고서 HTML 은 devlog README 의 Entries 에 넣지 않는다. 색인은 서버가 맡는다.
데이터·근거 파일은 devlog 규칙대로 `<project>/<topic>/data/` 에 두고, 보고서에는 수치만 옮긴다.

## 1. 문서 구조

이 순서가 검증된 순서다. 절을 빼도 되지만 **순서는 바꾸지 않는다** — 뒤 절이 앞 절을 전제한다.

```
00  아주 쉬운 설명      우리가 만드는 것 / 무엇이 문제인가 / 그래서 무엇을 했나
    └ 핵심 기전을 비유 하나로 설명하고, 그 비유의 한계까지 짚는다
01  한 장 요약          KPI 4개 + 결론 3개. 이것만 읽어도 되게
02~  본문               측정 / 조사 / 분석. 각 절은 "어떻게 쟀나 → 결과 → 무슨 뜻인가"
NN  실행 계획           할 것 / 하지 말 것. 하지 말 것에도 이유를 붙인다
NN  검증 기록           ★ 필수. §3
    지금 확실한 것 / 아직 모르는 것
※   참고 문헌           §5
⌘   용어집             §2
```

각 절에 **그림을 최소 하나** 넣는다(§2.5). 숫자만 나열된 절은 대개 덜 설명한 절이다.

**0장의 비유는 공들여 쓴다.** 비유가 좋으면 나머지가 다 읽히고, 나쁘면 아무것도 전달되지 않는다.
그리고 **비유가 어디서 깨지는지 반드시 같이 쓴다** — 읽는 사람이 바로 떠올릴 반례를 먼저 다뤄주면
문서의 신뢰가 올라간다. (예: "전역 평균 풀링은 믹서다" → "그럼 같은 사람이 뒤돌면?" → 재서 답한다)

## 2. 용어집과 팝업

- **가나다순이 아니라 이해하는 순서로 배열한다.** 앞 항목만 알면 다음이 읽히게.
- 항목마다 한 줄 정의 + 가능하면 `<dd class="ex">` 비유. 비유는 팝업에서 제외된다.
- 본문에서 처음 나오는 용어에 `<a class="t" href="#g-키">` 를 단다. 같은 용어를 매번 달 필요는 없다.
- **팝업 문구를 따로 쓰지 않는다.** 템플릿의 스크립트가 용어집 `<dd>` 를 긁어 만든다.
  용어집을 고치면 팝업이 따라 바뀐다 — 두 곳을 고치게 만들면 반드시 어긋난다.

팝업 구현에서 실제로 겪은 함정 두 개가 템플릿에 이미 해결돼 있다. 직접 다시 만들지 말 것.

| 함정 | 증상 |
|---|---|
| 가짜 요소(`::after`)로 만들기 | `overflow:auto` 인 표 안의 용어에서 **통째로 잘린다** |
| `left:50%` 중앙 정렬 | 화면 좌우 끝 용어에서 말풍선이 화면 밖으로 나간다 |

템플릿은 말풍선 하나를 `<body>` 에 `position:fixed` 로 띄우고, 폭을 재서 화면 안으로 클램프하고,
**화살표 위치를 따로 보정**한다(말풍선만 밀면 화살표가 엉뚱한 곳을 가리킨다).

## 2.5 그림으로 설명한다 — 적극적으로

**글로 두 문단 걸릴 것이 그림 하나로 끝나면 그림을 그린다.** 보고서 한 편에 **그림 4~8개**가 보통이고,
그보다 적으면 대개 덜 그린 것이다. 다만 장식은 넣지 않는다 — 아래 질문에 답이 안 되면 그 그림은 뺀다.

> **이 그림이 없으면 독자가 무엇을 놓치는가?**

### 무엇을 언제 그리나

| 전달할 것 | 형태 |
|---|---|
| 처리 흐름·구조 | **파이프라인 도식** — 상자와 화살표. 문제 지점만 붉은 테두리로 |
| 두 조건의 차이 | **막대 비교** — 두 값 사이 간격 자체가 메시지면 간격에 이름을 붙여 표시 |
| 누적·추세 | **꺾은선** — 기준선(무작위·기준값)을 점선으로 같이 깐다 |
| 비율 | 표로 충분하다. **원형 차트는 쓰지 않는다** — 각도는 비교가 어렵다 |
| 기전·원리 | **단계 도식 + 애니메이션** — 아래 참조 |

### 규칙

- **인라인 SVG 만 쓴다.** 외부 이미지·CDN·폰트를 쓰지 않는다. 문서는 파일 하나로 끝나야 한다.
- 색은 의미로만 쓴다: 파랑 `#2f6fd0` = 정상·같은 것, 빨강 `#cf4a3e` = 문제·다른 것. 장식 색을 늘리지 않는다.
- **색만으로 구분하지 않는다.** 모양·위치·라벨을 같이 쓴다.
- `fill="currentColor"` 로 그리면 다크 모드가 저절로 따라온다. 고정 색은 강조에만.
- 숫자는 그림 안에 직접 적는다. 범례를 따라가게 만들지 않는다.
- `role="img"` 와 `aria-label` 을 붙인다. `<figcaption>` 에 **무엇을 보라는 건지** 한 줄.
- 가로 스크롤이 생기지 않게 `viewBox` 를 쓰고 폭은 `max-width:100%`.

### 애니메이션

**움직임은 설명할 때만 쓴다.** 세 가지 용도 외에는 쓰지 않는다.

1. **단계 보여주기** — 기전을 1·2·3 단계로 나눠 차례로 보여준다. 0장 비유를 설명할 때 가장 효과가 크다.
2. **등장** — 막대·곡선이 화면에 들어올 때 자라난다. 눈이 그래프를 읽는 순서를 잡아준다.
3. **비교** — 전/후를 토글하면 같은 자리에서 바뀐다. 두 그림을 나란히 놓는 것보다 차이가 선명하다.

지켜야 할 것:

- **자동 반복 금지.** 계속 움직이면 읽는 것을 방해한다. 단계 도식은 **한 번 돌고 멈추거나, 누를 때 넘어가게** 한다.
- **0.4초 이내.** 길면 기다리게 된다.
- **애니메이션 없이도 완전해야 한다.** 멈춘 상태가 최종 상태여야 하고, 인쇄해도 정보가 다 보여야 한다.
- **`prefers-reduced-motion: reduce` 를 반드시 처리한다.** 템플릿에 이미 들어 있다 — 끄면 즉시 최종 상태로 간다.
- JS 가 꺼져도 내용이 보여야 한다. 템플릿의 등장 애니메이션은 **기본이 보이는 상태**이고 JS 가 있을 때만 숨겼다 보여준다.

템플릿에 바로 쓸 수 있는 부품이 들어 있다. 직접 만들지 말고 복사해 쓴다.

| 부품 | 쓰는 법 |
|---|---|
| 등장하는 막대 | `<rect class="gw" data-w="320">` — 화면에 들어오면 0에서 그 폭까지 자란다 |
| 그려지는 선 | `<polyline class="dr">` — 왼쪽부터 그려진다 |
| 단계 도식 | `<div class="steps">` + `<div class="step">` — 버튼으로 단계를 넘긴다 |
| 숫자 세기 | `<span class="cu" data-to="68">0</span>` — 0에서 목표값까지 센다 |
| 전/후 토글 | `<div class="ba">` + `<button class="batog">` — 같은 자리에서 바뀐다 |

## 3. 검증 기록 — 이 스킬에서 가장 중요한 절

**하위 에이전트나 외부 조사 결과를 그대로 옮기지 않는다.** 보고서에 넣기 전에 직접 확인하고,
**재현 실패한 것을 문서에 남긴다.**

- 숫자 주장 → 가능하면 재계산한다. 통계값은 직접 다시 돌린다.
- 코드 주장("이 저장소에 X가 없다") → `grep` 으로 확인한다.
- 논문 주장 → §5.
- 확인 못 한 것은 **"미검증"으로 표시하고 남긴다.** 지우면 다음 사람이 또 믿는다.

검증 기록 절은 표 하나로 충분하다: `보고된 주장 | 직접 확인 | 확인/불일치/부분`.

> 이 규칙이 있는 이유를 문서에 한 줄 적는다. 예:
> "이 프로젝트에서 '효과가 있다'고 보였던 것 7건이 전부 측정 오류였고,
> 자기가 만든 결과를 자기가 검증한 경우엔 한 번도 못 잡았다."

## 4. 개인정보·민감 이미지

- **기본은 넣지 않는다.** CCTV 크롭, 얼굴, 내부 화면 캡처 등.
- 넣지 않고도 설명되는지 먼저 시도한다 — 수치표, 인라인 SVG 도식, 막대/곡선 차트로 거의 다 된다.
- 꼭 필요하면 넣되 **그 문서를 서버에서 잠근다**(§6).
- 완성 후 반드시 확인:

```bash
grep -c '<img\|data:image' report.html     # 0 이어야 한다
grep -o 'href="https\?://[^"]*"' report.html | sort -u   # 허용한 도메인만 있어야 한다
```

- 외부 호스팅(claude.ai 아티팩트 등)은 **먼저 묻는다.** 한 번 올리면 캐시·색인이 남는다.

## 5. 논문 인용

**번호를 받아 적지 말고 직접 확인한다.** arXiv 는 공식 API 한 번이면 된다.

```
WebFetch http://export.arxiv.org/api/query?id_list=<쉼표로 나열>&max_results=30
  → 각 항목의 id, 연도, 제목을 한 줄씩 뽑아 주장과 대조
```

- bash 에서 외부 네트워크가 막혀 있을 수 있다. 그때는 `WebFetch` 를 쓴다.
- **제목이 일치한 것만 싣는다.** 불일치하거나 응답이 없으면 뺀다.
- 각 항목: 제목 · 저자/학회 · arXiv 링크 · **3~4줄 요약** · **"이 보고서에서 — 어디에 썼는지" 한 줄**.
  마지막 줄이 핵심이다. 그게 없으면 참고문헌이 장식이 된다.
- 본문에는 `<sup class="c"><a href="#r3">[3]</a></sup>` 로 단다.
- **머리에 한계를 적는다**: 제목은 확인했지만 논문 안의 개별 수치까지 원문 대조하지는 않았다면 그렇게 쓴다.

인용 번호는 어긋나기 쉽다. 마지막에 반드시 기계로 검사한다(§7).

## 6. 호스팅

문서 하나만 띄우지 말고 **주제별 색인**으로 올린다. 스킬에 포함된 `scripts/serve_devlog.py` 가 이미 그렇게 한다.
보고서를 만들면 묻지 않고 서버를 띄운다(이미 떠 있으면 그대로 둔다). 기본은 LAN 에 여는 `0.0.0.0` 이다.
스크립트는 이 스킬 디렉토리 안에 있고, `${CLAUDE_PLUGIN_ROOT}/skills/techreport/scripts/` 로도 같은 파일을 가리킨다.

```bash
bash <이 skill 디렉토리>/scripts/serve_devlog.sh docs/devlog [포트]   # 기동 (멱등). 기본 포트 8800
REPORT_HOST=127.0.0.1 bash <이 skill 디렉토리>/scripts/serve_devlog.sh docs/devlog   # 이 머신에서만 볼 때
kill "$(cat /tmp/serve_devlog.8800.pid)"                                           # 중지
```

`@reboot` cron 등록은 사용자가 원할 때만 한다. Linux 와 macOS 모두에서 동작한다.

| 규칙 | 이유 |
|---|---|
| **요청 경로를 파일 시스템에 넘기지 않는다** | 보고서 옆에 민감 파일이 수천 개 있다. 시작 시 만든 **허용 목록**의 키로만 찾는다 |
| 민감 이미지가 내장된 문서는 **기본 잠금** | 상시 서버다. `--include-personal` 로만 연다 |
| `X.html` 과 `X.artifact.html` 은 한 줄로 합친다 | 같은 문서다 |
| 주기적 재검색 | 새 보고서가 재시작 없이 올라온다 |
| 생존 확인은 **PID 파일 + 포트 리스닝** | `pgrep -f` 는 **자기 명령줄을 매치해** 뜨지도 않은 서버를 "실행 중"이라 보고한다. 실제로 당했다 |

LAN 에 열면 사내 누구나 본다. 이미지가 내장된 문서는 서버가 기본으로 잠그지만, 내부 경로·계정·IP 처럼 글로 든 민감 정보는 잠그지 못한다.
그런 내용이 있는 보고서를 만들었다면 띄우기 전에 `REPORT_HOST=127.0.0.1` 과 SSH 터널을 권한다.

## 7. 완성 검사 — 넘기기 전에 돌린다

`reference/checklist.md` 에 전체 목록이 있다. 기계로 확인할 수 있는 것은 전부 돌린다.

```bash
python3 - <<'PY'
import re, sys
h = open(sys.argv[1] if len(sys.argv)>1 else 'report.html').read()
ids  = set(re.findall(r'id="([^"]+)"', h))
anch = set(re.findall(r'href="#([^"]+)"', h))
print('끊긴 앵커  :', sorted(anch - ids) or '없음')
refs = set(re.findall(r'id="(r\d+)"', h)); used = set(re.findall(r'href="#(r\d+)"', h))
print('없는 인용  :', sorted(used - refs) or '없음')
print('미인용 문헌:', sorted(refs - used, key=lambda s:int(s[1:])) or '없음')
print('이미지     :', len(re.findall(r'<img|data:image', h)))
print('외부 링크  :', sorted({re.sub(r'(https?://[^/]+).*', r'\1', u)
                             for u in re.findall(r'href="(https?://[^"]+)"', h)}) or '없음')
print('용어 링크  :', len(re.findall(r'class="t" href="#g-', h)),
```

## 8. 만드는 순서

1. `templates/report.html` 을 "저장 위치"에서 정한 경로로 복사한다. 템플릿에는 CSS·팝업 스크립트·절 뼈대가 들어 있다.
2. 본문을 채운다. **0장 비유를 먼저 쓴다** — 비유가 정해져야 나머지 설명이 일관된다.
3. **그림을 그린다.** 절마다 하나씩, 0장 비유에는 단계 도식(§2.5).
4. 용어집을 채운다. 본문에서 설명 없이 쓴 낱말을 전부 쓸어 담는다.
5. 본문의 용어에 `class="t"` 링크를 단다.
6. 논문을 §5 절차로 검증하고 인용을 단다.
7. 검증 기록 절을 쓴다. **재현 실패를 반드시 포함한다.**
8. §7 검사를 돌린다.
9. `scripts/serve_devlog.sh docs/devlog` 로 서버를 띄우고(§6) 보고서 주소를 알려준다. 서버 PID·로그·중지 방법을 함께 적는다.
   보고서 주소는 색인 페이지의 `/d/<project>/<stem>` 이다.
