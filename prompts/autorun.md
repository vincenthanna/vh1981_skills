# autorun: 한 번에 끝까지 진행하는 작업 절차

이 문서는 작업 하나를 받아 조사, 실행, 검증, 보고까지 중간 확인 없이 진행하는 절차다.
autowork-share의 autowork 스킬에서 조직 전용 부분(Teleport, Jira, PLUSINSIGHT 사이트)을 걷어내고 범용 절차만 남겼다.
세션에 이 문서를 첨부하고 아래 "작업 지시서"를 채워 주면, Claude는 시작할 때 한 번만 질문하고 그 뒤로는 멈추지 않는다.
사람이 읽을 외부 게시물은 끝까지 초안으로만 남기며, 커밋과 push는 지시서에서 허용한 경우에만 한다.
끝나면 결과 요약, 초안, 보류 항목, 근거 위치를 정해진 형식으로 보고하고, 배운 점을 `autorun-learnings.md` 에 남긴다.

## 사용법

세션에서 이 문서를 첨부하고 지시서를 붙인다. 비워 둔 항목은 Claude가 기본값으로 채운다.

```
@~/repos/vh1981_skills/prompts/autorun.md

## 작업 지시서
작업: <무엇을 해야 하는지. Slack 스레드 원문, PR URL, 이슈 설명, 메모 등 무엇이든>
자료: <파일 경로, URL, 로그, 붙여넣은 텍스트>
완료 기준: <무엇이 관측되면 끝인지. 비우면 Claude가 정해서 0단계에 적는다>
허용: <커밋 | push | PR 생성 | 원격 서버 명령 | 설치 | 없음>   (기본값: 없음)
금지: <건드리면 안 되는 것>
보고 대상: <결과를 읽을 사람. 예: 나, 팀 Slack, PR 리뷰어, 비개발자>   (기본값: 나)
```

## 이 문서가 기본 규칙을 바꾸는 범위

이 문서를 첨부한 세션에서는 아래 세 규칙이 core 가이드라인보다 우선한다. 나머지 규칙은 그대로 적용한다.

| 기본 규칙 | autorun 안에서 |
|---|---|
| 모호한 요구는 질문한다 | 0단계에서 막히는 질문만 한 번에 묶어 묻는다. 그 뒤로는 합리적 기본값을 골라 진행하고 그 선택을 보고에 적는다 |
| 작업 중간 보고는 1~2문장 | 중간 보고 대신 `STATE.md` 를 갱신한다. 사용자가 물으면 그 파일 기준으로 답한다 |
| commit/push는 명시 요청 시에만 | 지시서의 "허용" 항목이 명시 요청이다. 거기 없으면 하지 않고 보류 항목으로 남긴다 |

외부 게시물을 초안으로만 남기는 규칙과 파괴적 동작 전에 확인하는 규칙은 autorun 안에서도 바뀌지 않는다.

## 작업 공간

모든 산출물은 작업마다 하나의 디렉토리에 모은다. `<slug>` 는 작업을 나타내는 짧은 영문 이름이다.

```
/tmp/autorun/<slug>/
  STATE.md          # 완료 기준, 진행 상태, 내린 결정, 보류 항목 (계속 갱신)
  FINDINGS-*.md     # 조사 결과 (subagent가 쓴 것 포함)
  EVIDENCE-*.md     # 검증 근거: 실행한 명령과 관측값
  DRAFT-*.md        # 사람이 읽을 글의 초안
  POST-QUEUE.md     # 보류한 외부 동작과 그 실행 명령
```

`STATE.md` 는 compact나 세션 재개 뒤에 작업을 이어 가는 기준이다. 단계를 넘어갈 때와 결정을 내릴 때마다 갱신한다.

## 진행 단계

### 0단계: 접수
목표: 작업을 이해하고 완료 기준을 확정한다.
- 지시서와 자료를 모두 읽고 요청 유형을 하나로 정한다. 유형은 조사, 수정, 데이터 추출, 질문 답변, 리뷰 대응, 운영 조치 중 하나다. 요청한 사람에게 충분히 답하는 가장 작은 작업 흐름을 고른다.
- 완료 기준을 관측 가능한 조건으로 쓴다. "로그에 X가 찍힌다", "테스트 N개 통과", "쿼리 결과 row 수가 M" 같은 형태다.
- 진행을 막는 질문이 있으면 이 단계에서 한 번에 묶어 묻는다. 환경 사실(접속 정보, 권한)과 되돌릴 수 없는 선택만 질문 대상이다. 나머지는 기본값을 골라 `STATE.md` 에 적는다.
- `autorun-learnings.md` 를 읽는다. 이 문서와 같은 디렉토리에 있다.
완료 기준: `STATE.md` 에 요청 유형, 완료 기준, 허용 범위, 기본값으로 정한 것이 적혀 있다.

### 1단계: 조사
목표: 원인이나 답을 근거와 함께 찾는다.
- 서로 독립적인 조사는 subagent로 병렬 진행한다. subagent는 결과를 `FINDINGS-<주제>.md` 에 쓰고 200단어 이내의 요약만 돌려준다. 본 세션은 요약과 결과 파일만 읽고 transcript는 읽지 않는다.
- 사실과 추측을 나눠 적는다. 추측에는 확인 방법을 붙인다.
- 정상 동작하는 쌍둥이(다른 서버, 다른 branch, 이전 버전)가 있으면 먼저 둘을 나란히 비교한다. 고장 난 쪽만 파고드는 것보다 원인이 빨리 보인다.
- 상태를 가진 작업(배치 job, 마이그레이션, 캐시를 쓰는 스크립트)은 실행해서 확인하지 않는다. 실행하면 진단하려던 출력이 바뀐다. 스크립트, 로그, 읽기 전용 쿼리로 조사한다.
- 주기적으로 도는 작업이 멈췄다면 "스케줄은 있는데 매번 실패한다"와 "스케줄이 없다"를 먼저 가른다. 로그 파일의 마지막 오류가 답인 경우가 많다.
완료 기준: 원인이나 답이 근거와 함께 `FINDINGS-*.md` 에 있고, 남은 추측은 추측이라고 표시돼 있다.

### 2단계: 실행
목표: 요청 범위 안에서 문제를 해결한다.
- 범위는 요청한 것까지다. 옆에서 발견한 문제는 고치지 않고 `STATE.md` 의 후속 과제로 적는다.
- 되돌릴 수 있는 작업부터 한다. 변경 전 상태를 백업하거나 기록해 두어 롤백할 수 있게 한다.
- 수정 방안이 둘 이상이고 우열이 분명하지 않으면 각 방안을 짧게 비교해 하나를 고르고, 고른 이유를 `STATE.md` 에 적는다. 큰 변경이면 worktree에서 시도한다.
- 지시서가 허용하지 않은 동작과 파괴적 동작(데이터 삭제, 운영 서비스 재시작, force push)은 실행하지 않는다. 실행 명령과 함께 `POST-QUEUE.md` 에 적고 나머지 작업을 계속한다.
- 막히면 무엇 때문에 막혔는지 정확히 적고, 그것에 의존하지 않는 일을 끝까지 한다. "X 권한이 없어 Y를 못 했다"는 그 자체로 유효한 결과다.
완료 기준: 허용 범위 안의 변경이 모두 끝났고, 보류한 동작은 `POST-QUEUE.md` 에 있다.

### 3단계: 검증
목표: 완료 기준이 실제로 충족됐는지 실행 근거로 확인한다.
- 0단계의 완료 기준마다 실행 근거를 `EVIDENCE-*.md` 에 남긴다. 실행한 명령과 관측값(로그 줄, HTTP 코드, row 수, 테스트 결과, 컨테이너 시작 시각, CI run ID)을 그대로 적는다. 코드만 보고 PASS라고 하지 않는다.
- 근거 파일은 PASS/FAIL 표를 맨 위에 두고, 그 아래에 근거 발췌를 둔다.
- 코드를 바꿨으면 code-reviewer agent로 독립 리뷰를 받는다. 기본은 1개, 인프라·보안·데이터 변경이면 3개를 같은 프롬프트로 돌린다. 하나라도 수정 요청이 나오면 고치고 다시 받는다.
- push가 허용됐다면 CI가 끝날 때까지 감시한다. 디스크 부족이나 네트워크 같은 인프라 원인으로 실패하면 다시 돌린다. 세 번 실패하면 workflow를 진단한다.
- 운영 환경 검증이 FAIL이면 백업으로 롤백하고 FAIL 근거를 남긴 뒤 멈춘다. 운영 환경에서 실패한 수정을 자동으로 다시 시도하지 않는다.
완료 기준: 모든 완료 기준에 PASS 근거가 있다. 또는 FAIL 근거와 롤백 기록이 있다.

### 4단계: 초안과 보고
목표: 사람이 읽을 글을 초안으로 만들고 결과를 보고한 뒤 멈춘다.
- 지시서의 보고 대상에 맞춰 `DRAFT-*.md` 를 쓴다. Slack, PR 답글, PR 본문, 메일 같은 외부 게시물은 humanizer 스킬로 다듬는다. 비개발자가 읽는다면 humanizer의 진행 보고 모드를 쓴다.
- 보낼 명령을 `POST-QUEUE.md` 에 순서대로 적는다. PR 본문은 `--body-file` 로 넘기는 명령으로 적는다.
- 최종 보고를 아래 형식으로 출력하고 멈춘다.
- 사용자가 보내라고 하면 `POST-QUEUE.md` 를 위에서부터 실행하고 각각 반영됐는지 확인한다.
완료 기준: 최종 보고가 출력됐고 외부 동작은 하나도 실행되지 않았다.

### 5단계: 회고
목표: 다음 실행이 더 빨라지도록 배운 점을 남긴다.
- `autorun-learnings.md` 에 날짜를 붙인 한 줄씩 추가한다. 실패한 명령과 성공한 형태, 틀린 가정, 사용자가 초안에서 고친 부분, 불필요하게 멈췄거나 멈췄어야 했던 지점이 대상이다.
- 특정 repo나 서버에만 해당하지 않게 일반화해서 쓴다. 배운 것이 없으면 쓰지 않는다.
- 같은 교훈이 두 번 나오면 이 문서 본문에 반영하자고 보고에서 제안한다. 본문은 사용자 승인 없이 고치지 않는다.
완료 기준: 새 교훈이 기록됐거나, 없다는 것이 보고에 한 줄로 적혀 있다.

## 최종 보고 형식

```
## 결과
<2~3줄: 무엇이 끝났고 무엇이 바뀌었는지>

## 초안
<DRAFT-*.md 원문. 여러 개면 각각>

## 보류 항목
<POST-QUEUE.md 의 동작, 막힌 일과 막힌 이유, 후속 과제>

## 기본값으로 정한 것
<0~2단계에서 질문 대신 고른 선택과 이유>

## 근거
/tmp/autorun/<slug>/ 와 그 안의 주요 파일
```

## 멈추고 묻는 경우

0단계 이후에 사용자에게 묻는 경우는 아래 네 가지뿐이다. 그 밖의 문제(CI 인프라 실패, 막힌 subagent, 경로 탐색)는 스스로 해결한다.

1. 수정 방안들의 우열을 근거로 가를 수 없고, 잘못 고르면 되돌리기 어렵다.
2. 운영 환경 검증이 FAIL해서 롤백했다.
3. 해결하려면 요청 범위를 벗어나야 한다.
4. 지시서에서 허용하지 않은 동작 없이는 남은 일을 하나도 진행할 수 없다.

## 리뷰 대응일 때

요청 유형이 PR 리뷰 대응이면 위 단계에 다음을 더한다.

- 리뷰와 인라인 코멘트를 모두 가져온다.

  ```bash
  gh api repos/<org>/<repo>/pulls/<N>/reviews
  gh api repos/<org>/<repo>/pulls/<N>/comments
  ```

- 코멘트마다 처리 방침을 정한다. 수정, 답변만, 범위 밖 분리 중 하나다.
- 코멘트마다 답글 초안 `DRAFT-reply-<comment-id>.md` 를 쓴다. 리뷰어의 지적을 1~2문장으로 받고, 바꾼 내용과 커밋 SHA를 적고, 검증 근거를 요약한다. 언어는 기존 PR 대화의 언어를 따른다.
- PR 본문 초안에 "Review cycle N" 절을 추가한다. 코멘트별 처리 표와 검증 결과 표를 넣고, 범위 밖 지적은 Follow-ups로 적는다. N은 본문에 있는 기존 절 수에 1을 더한 값이다.
- PR 제목은 원래 제목이 틀리게 된 경우가 아니면 바꾸지 않는다.
- 리뷰 재요청 명령을 `POST-QUEUE.md` 에 넣는다.

  ```bash
  gh api -X POST repos/<org>/<repo>/pulls/<N>/comments/<comment-id>/replies -F body=@DRAFT-reply-<comment-id>.md
  gh api repos/<org>/<repo>/pulls/<N> -X PATCH -F body=@DRAFT-pr-body.md
  gh api -X POST repos/<org>/<repo>/pulls/<N>/requested_reviewers -f 'reviewers[]=<login>'
  ```
